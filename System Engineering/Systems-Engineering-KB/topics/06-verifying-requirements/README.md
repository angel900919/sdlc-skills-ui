# Verifying Requirements

> Domain: Requirements & Modeling · Learning order: 6 · Bloom target: Apply

## Overview

Verifying requirements answers the question "did we build the *requirement* right?" — is each statement specific, measurable, achievable, relevant, and testable *before* anyone designs or builds against it (source: m2-verify). Unverified requirements mean "you're building on assumptions, not specifications," and only-defined, incomplete, or unrealistic requirements lead to costly failures, delays, and stakeholder dissatisfaction (source: m2-verify, master-notes). Note the contrast: verifying requirements here is about the *quality of the written statement*; **validation of the built system** ("did we build the right system?") is a separate, later activity covered in [16-verification-validation-methods](../16-verification-validation-methods/README.md). **What you already know that connects here**: [05-requirements-elicitation-analysis](../05-requirements-elicitation-analysis/README.md) — you must first elicit and classify requirements before you can check whether each one is well-formed and verifiable.

## Learning objectives

After this topic you will be able to:

- (Apply) Judge whether a given requirement is verifiable using the SMART criteria, and explain why for each.
- (Apply) Rewrite a vague requirement into a SMART one with quantified, testable conditions.
- (Apply) Write a requirement using the standardized `[system] shall [function] [measurable condition] [under conditions]` template.
- (Understand) Explain how peer reviews and walkthroughs catch unverifiable requirements before design.
- (Understand) Distinguish verifying a requirement statement from validating the delivered system.
